01你需要先理解的「软件世界」

在跳进 LLM 和 Agent 之前，先把这些词钉一下。它们是你看任何项目代码的前提。

前端 / 后端 frontend / backend

前端 = 浏览器里看到的页面；后端 = 在服务器上跑的程序，负责数据和逻辑。

类比：前端是餐厅里看到的菜单和服务员，后端是厨房。你点菜（点按钮）→ 服务员（前端）把订单传给厨房（后端）→ 厨房做完菜（处理数据）→ 服务员端上来（前端展示结果）。
这个项目里：前端是 Three.html、admin.html 和 js/*.js；后端是 server.py 和它调用的 interpret_*.py 一堆。
HTTP 请求 HTTP request

前端向后端"提一个要求"的标准格式：方法（GET / POST...）+ 路径（/api/...）+ 可选 body。

类比：寄一封挂号信。GET 像"问个问题"（取某个东西），POST 像"递交一份资料"（让对方处理一件事）。信封上的地址 = 路径，信里写的内容 = body。
这个项目里：当你点"生成解读"按钮，前端就发出 POST /api/interpret/6，body 里塞 {style, language, question}。后端在 server.py:_handle_interpret_stream() 里接收。
API 端点 API endpoint

后端对外暴露的一个"门"，每个门对应一项服务。

类比：邮局窗口。寄件、取件、换零钱、办护照各有一个窗口，门牌号就是端点 URL。
这个项目里所有的门：
  • GET /api/readings — 列出已保存的牌阵
  • POST /api/readings — 保存一次新牌阵
  • POST /api/interpret/<id> — 让 AI 解读某个牌阵
  • GET /api/interpret/<id>/agent-trace — 看 Agent 推理过程
JSON JavaScript Object Notation 读作 "Jay-Sun"

前后端之间通信用的统一文本格式，是所有现代 Web 服务的"通用语言"。

类比：国际通用的快递单格式 — 谁都看得懂、谁都能填。{} 是大括号包起来的"对象"，[] 是方括号包起来的"列表"。
例子：POST /api/interpret/6 的 body 就是 JSON： 
{"style":"traditional","language":"zh","question":"我应该跳槽吗？"}
数据库 / SQLite database / SQLite

数据库 = 结构化存数据的地方，能查询、能更新。SQLite 是其中最轻的一种：整个库就一个文件。

类比：普通文件像便利贴一摞，找东西得翻；数据库像有索引的档案柜。SQLite 像随身带的小档案盒（不需要单独的服务器进程）。
这个项目里：data/tarot.sqlite3 一个文件存了所有 reading、interpretation、agent trace、设置。server.py 顶部用 sqlite3 这个 Python 自带模块连上去。

为什么选 SQLite 而不是 PostgreSQL/MySQL？这是个"本地优先"应用 — 不需要联网、不需要账号、单机能跑。SQLite 零配置、零依赖。

SSE 流式 Server-Sent Events

服务器持续往前端推数据的简单协议。一次 HTTP 连接保持开着，服务器一段一段写。

类比：普通 HTTP = 你点一份外卖等齐了再送来；SSE = 厨师做一道菜就先端一道，吃着等下一道。
关键体验：AI 解读用 SSE — 你能看到字一个一个蹦出来，不用干等十几秒。每一帧长这样： 
data: {"chunk": "在"}

data: {"chunk": "过去"}

data: {"chunk": "你"}
实现在 server.py:_handle_interpret_stream。

🎯 自查：到这里你应该能回答

  • "用户点解读按钮"之后到"第一个字蹦出来"之间，至少经过了哪三步？
  • 如果数据库文件被删了，重启后还能登录吗？为什么这个项目这个问题不成立？
  • SSE 跟普通 HTTP 的区别在用户体感上是什么？

02LLM 基础术语

LLM = Large Language Model，大语言模型。这一节把围绕它的核心词全部理清。

大语言模型 Large Language Model (LLM)

一个超大的神经网络，输入一段文字，输出"接下来最可能的文字"。

类比：极其博学的接龙游戏选手。给它"今天天气真好，我想"，它会接"出去散步"或"睡个懒觉"。它不"理解"任何东西，只是把见过的海量文字的统计规律记住了。
项目里用了两个 LLM：
  • qwen2.5:7b — 千问 7B 模型，跑在你本机 Ollama 上，做主力解读
  • nomic-embed-text — 嵌入模型，把文本变成向量（下面会讲）
参数 / 7B parameters / 7B

"7B" = 7 Billion = 70 亿。指这个神经网络里有 70 亿个可调旋钮。

类比：你脑袋里大概 860 亿个神经元 + 100 万亿个突触。LLM 的"参数"接近这个突触的概念 — 越多通常越聪明，但跑起来越费内存。
为什么选 7B：14B 跑不动你的 6GB 显存（RTX 3060），3B 又太蠢。7B 在 Q4_K_M 量化后约 4.5GB，刚好塞得下。

同一个家族常见尺寸：1.5B / 3B / 7B / 14B / 32B / 72B。商业大模型像 GPT-4 估计在 1T（1 万亿）量级，但官方没公布。

量化 quantization / Q4_K_M

把模型参数从高精度（float32 / 4 字节）压缩到低精度（int4 / 0.5 字节）的过程，体积小 8 倍，速度快好几倍，质量略降。

类比：JPEG 压缩照片 — 文件小很多、人眼几乎看不出区别。Q4_K_M 是种特定算法（K-quants Medium）。
实例：原版 qwen2.5:7b 大约 15GB，Q4_K_M 量化版只有 4.5GB，6GB 显存能跑。
Token / Tokenization token

模型处理文本的最小单位，不是字也不是词，而是"被切分算法切出来的片段"。

类比：把整本书撕成不规则的小纸条 — 常用词一片一张纸，罕见词被切成几片。"hello"通常是 1 个 token；"reinforcement"可能切成 "rein" + "force" + "ment"。中文常常一个汉字一个 token。
具体数字：项目里 DEFAULT_NUM_PREDICT = 600 意思是"最多让模型生成 600 个 token"。中文一般 1 字 ≈ 1 token，所以约 300-500 字的解读够用。

为什么不直接按字符？因为按 token 模型对常见词更敏感，对罕见词又能拆开处理，是个权衡好的折中。

提示词 prompt

你给模型的输入文本。LLM 看到 prompt 接下去生成下文 — 改 prompt 就是改模型的输出方向。

类比：给作家一个开头，让他续写。你给的开头不同，故事走向就完全不同 — 这就是 "prompt engineering" 的本质。
看看长啥样：interpret_prompts.py 整个模块就是在拼 prompt。一次解读的完整 prompt 包含：
  1. System prompt — "你是一个塔罗解读师..."
  2. Few-shot — 一个手写的高质量例子（参考样本）
  3. 检索块 — RAG 拉来的 3 张牌的标准牌义（【参考资料】）
  4. 用户的问题（如果有）
  5. 当前牌阵的牌名 + 位置
System / User / Assistant 角色 system / user / assistant role

现代 chat-style LLM 把对话拆成"几个角色"，按顺序排好。模型只在 assistant 角色处生成。

类比：剧本里的角色标签。System 是导演给演员的总指令，user 是观众递上来的提问，assistant 是演员的台词。
看代码： 
messages = [
    {"role": "system", "content": "你是一个塔罗解读师..."},
    {"role": "user",   "content": "我抽到了隐士、世界逆位、死神逆位..."}
]
这就是发给 Ollama 的 messages 数组。Ollama 自动补一个 assistant 角色，开始生成。
温度 temperature

控制生成随机性的旋钮。0 = 永远选最可能的下一个 token（呆板）；1+ = 更随机有创意（也更容易跑偏）。

类比：厨师做菜的"敢不敢加非常规调料"。低温 = 教科书操作；高温 = 即兴发挥。
项目里两套设定：
  • 解读生成（要散文感）：temperature = 0.78
  • JSON 模式分类/审查（要稳定）：temperature = 0.2
流式生成 vs 批量生成 streaming vs non-streaming

流式 = 模型生成一个 token 就吐一个；批量 = 全部生成完才一次性返回。

项目里同时用了两种：
  • 解读生成 → 流式（用户能边看边读）
  • classify / critique → 批量（要的是结构化 JSON，必须完整才能解析）
见 interpret_service.stream_ollama 和 interpret_agent.call_ollama_json。
JSON 模式 JSON mode / structured output

告诉 LLM"你的输出必须是合法的 JSON 对象"，模型在内部约束自己只生成合法 JSON。

类比：跟人对话时说"用是/否回答"，然后他真的只说"是"或"否"，不会自由发挥。
关键调用：interpret_agent.py:call_ollama_json，body 里加 "format": "json"。 
body = {
    "model": model,
    "stream": False,
    "format": "json",          # ← 这一行
    "messages": messages,
    "options": {"temperature": 0.2, "num_predict": 120}
}

为什么仍然需要容错解析？因为 JSON 模式不是 100% 可靠 — 偶尔模型会在 JSON 前面加一句"Sure, here you go:"。所以我们有一段正则兜底，提取出第一个 {...} 块。

🎯 自查

  • 你能用一句话解释为什么解读用 temperature=0.78 但分类器用 0.2 吗？
  • 如果模型的 JSON 输出前面多了一行解释文字，项目里的哪个机制会兜住？
  • token 跟"字"不一样，那"600 token"对中文文章大约多少字？

03RAG（检索增强生成）

这是 Agent 项目的核心技能之一。RAG = Retrieval-Augmented Generation。先讲组件，再讲为什么需要。

向量 / Embedding embedding / vector

把一段文字变成一串数字（一个向量）。语义接近的文字，向量也接近。

类比：给每个词一组 GPS 坐标。"苹果"和"梨"的坐标接近（都是水果），"苹果"和"汽车"离得远。LLM 内部就是用类似的坐标体系运作的。
具体细节：项目用 nomic-embed-text 模型，输出 768 维向量（768 个浮点数）。一句话"我应该跳槽吗"会变成 [0.123, -0.456, 0.789, ...] 这样 768 个数字。

为什么 768？是这个模型训练好的固定输出大小。不同模型不同维度，比如 OpenAI 的 text-embedding-3-small 是 1536 维。

余弦相似度 cosine similarity

衡量两个向量"指向同一方向"的程度。值在 -1 到 1 之间，越接近 1 越相似。

类比：两个箭头夹角越小，余弦越接近 1（一个方向）；垂直 = 0（无关）；反方向 = -1（相反）。
看代码：interpret_rag.py:_cosine 算的就是 (A·B) / (|A| · |B|)。用户问"我应该跳槽吗" → 嵌入成向量 → 跟语料库里 3 张牌的向量逐一求余弦 → 排序。

实际项目里你看到过这个数字：

retrieve: count=3 topic_bias=career
  - card_id=21 orient=reversed score=0.6089  ← 世界逆位
  - card_id=9  orient=upright score=0.5756  ← 隐士
  - card_id=13 orient=reversed score=0.5554  ← 死神逆位
语料库 corpus

用于检索的预先准备好的文本集合。RAG 时刻不需要现场生成，而是从语料库里捞最相关的几条。

这个项目的语料库：data/tarot_corpus.json，156 条 = 78 张牌 × 正/逆位。每条结构： 
{
  "card_id": 18,
  "zh": "月亮",
  "en": "The Moon",
  "orientation": "reversed",
  "themes": ["clarity", "release of fear"],
  "imagery": "灰暗的月光下，犬狼狂吠...",
  "situations": {
    "career": "迷雾散去，看清同事关系的真相",
    "relationship": "误会得以澄清",
    ...
  },
  "keywords": ["释放", "澄清", "看穿幻象"]
}
向量数据库 vector database / vector store

专门存储向量、快速找最近邻的存储系统。常见有 Pinecone / Chroma / Qdrant 等。

项目没用第三方：156 条这个规模太小了，自建 SQLite 里存 BLOB（二进制 float32）+ 全表余弦遍历比引入向量数据库还快。

表结构：

CREATE TABLE corpus_embeddings (
    entry_key TEXT,        -- "18:reversed"
    model TEXT,            -- "nomic-embed-text"
    corpus_sig TEXT,       -- 语料的指纹
    dim INTEGER,           -- 768
    vector BLOB,           -- 768 × 4 字节
    text_hash TEXT,
    created_at TEXT
);

156 条规模下，全表余弦计算每次 < 50ms。如果语料涨到 10 万条以上，就该上 Chroma/Qdrant 之类专门库了 — 它们用 HNSW 等近似算法把查找做到 O(log n)。

RAG Retrieval-Augmented Generation

在让 LLM 生成前，先从语料库捞几条最相关的资料拼进 prompt，让模型有"参考书"可以引用。

类比：考试时不准开卷的学生 vs 半开卷的学生。开卷的会先翻找相关章节，再下笔回答 — RAG 就是给 LLM 半开卷的能力。
完整流程：
  1. 用户抽到 3 张牌，问"我应该跳槽吗"
  2. Retrieve：从语料库找这 3 张牌对应的解释 + 按问题排序
  3. 把找到的解释作为【参考资料】拼进 prompt
  4. Generate：LLM 看着参考资料 + 问题 + 牌名生成解读
实现：interpret_rag.py:retrieve_for_cards

没 RAG 会怎样？LLM 凭训练时"模糊记忆"瞎编 — 大概率说得过去，但会编造塔罗书里不存在的细节（俗称"幻觉" hallucination）。有 RAG 的输出更"言之有据"。

两阶段过滤 two-stage filter

先做便宜的精确过滤，再做贵的语义排序。

这是本项目 RAG 的关键设计：
  1. 阶段一（确定性）：根据 card_id + 正逆位精确匹配 — 抽到隐士正位就只取"9:upright"那一条。不用调嵌入模型，零成本。
  2. 阶段二（语义重排）：只有用户提供了问题时才跑 — 把问题嵌入成 768 维向量，跟阶段一的候选向量求余弦，排序。
没问题 → 直接走阶段一（快路径）。有问题 → 阶段一过滤 + 阶段二排序。
嵌入缓存 / 幂等构建 embedding cache / idempotent build

嵌入算一次就存起来，下次不用再算。幂等 = 反复跑同一操作结果不变。

项目实现：缓存键是 (corpus_signature, model, text_hash)。语料没改就跳过；改了任一条文本就重新嵌入那一条。

第一次构建 156 条要 5-6 分钟（每条调一次 Ollama embed），之后只要语料不动，零开销。看 interpret_rag.py:build_index。

🎯 自查

  • "幻觉"（hallucination）是什么意思？RAG 怎么减少它？
  • 项目里如果用户不提问题，RAG 还跑吗？跑哪一阶段？
  • 把语料从 156 涨到 100 万条，为什么这套实现就该换成 Chroma/Qdrant？

04Agent 系统

RAG 只是 Agent 的一个组件。Agent 整体是一条"多步推理管道"。

Agent agent

能在多个工具/步骤之间编排的 LLM 应用。不是单次问答，而是规划 → 工具调用 → 评估的循环。

类比：普通 LLM 像"一句问一句答"的接线员。Agent 像项目经理：接到任务后先想要做哪几步，调几个外部工具（搜索/数据库/计算器），最后整合结果交付。
本项目的 Agent 管道：
classify → retrieve → generate → critique
每一步都是一次独立的 LLM 调用，结果存到 agent_steps 表。

注意：Agent ≠ 多轮对话。Agent 强调"内部多步"，而多轮对话强调"对话历史"。一个 Agent 可以是单轮触发的（像这个项目）。

Classify（分类） classify

第一步：用 LLM 把用户问题归到一个事先定好的标签集合里。

项目里分三个维度：
  • topic：career / relationship / health / growth / general
  • intent：decision / clarity / timing / perspective
  • tone：anxious / curious / grieving / hopeful / neutral
输出严格 JSON。看 interpret_agent.py:classify。

为什么这一步有价值？拿到 topic 可以给检索器"主题提示"，也是后续观察/评测的基础数据。

闭集词汇 closed-vocab / enum constraint

事先定好的有限标签集合，模型必须从里头选，不能自创。

类比：选择题 vs 简答题。闭集就是选择题 — 答案在四个选项里，不会冒出第五个。
实现细节：JSON 模式只是"格式正确"，不保证标签合法。所以代码里有 _coerce_enum() 做后处理：模型返回 "career-decision" 也会被映射回 "career"；返回 "astrology" 这种不在表里的，会回退到默认 "general"。

核心代码：

def _coerce_enum(value, allowed, fallback):
    if isinstance(value, str):
        v = value.strip().lower()
        if v in allowed:
            return v
        # 容忍简单别名
        for opt in allowed:
            if v.startswith(opt) or opt in v:
                return opt
    return fallback
Critique（自我审查） critique / self-critique

让另一个 LLM 调用扮演"批改老师"，给已生成的内容打分、指出问题。

类比：写完作文交给同事看一眼再寄出去。同事不会重写，只会标"这段太空、这段没回应问题"。
实现：interpret_agent.py:critique 让 qwen2.5:7b 看着生成结果 + 用户问题 + 抽到的牌，输出： 
{
  "score": 0..10,
  "issues": ["off_topic", "missing_card", "slop_phrase", ...],
  "needs_retry": false,
  "summary": "一句话总结"
}
实测出 8.17/10 的平均分。

关键设计：critique 在 stream 完之后跑（finally 块里），用户看完结果它才开始 — 不增加用户感知延迟。

为什么不让 critique 触发重写？因为 critique 自己也可能错。当前设计是先把信号收集起来（写进 agent_steps），后面如果发现某类问题反复出现，再决定要不要加重写逻辑。这是工程上"宁可观察不可乱动"的原则。

优雅降级 graceful degradation

某个组件挂了不让整个系统挂，而是降级运行。

项目里的降级链：
挂了什么降级行为
Ollama 本机服务切到 OpenRouter（如果配了 key），否则报错给前端
嵌入模型缺失跳过语义重排，只走 card_id 精确匹配
分类器失败用默认 (general / clarity / neutral)，主流程不停
审查员失败用户已经看到答案了，只是少了一条审查日志
核心原则：Agent 链路上任何一环都不能阻塞用户感知。
Trace（推理链路） trace

一次 Agent 运行从头到尾每一步的完整记录。可回放、可分析、可调试。

实现：agent_steps 表，每次运行一个 trace_id（UUID hex），把 4 步全量记下来：输入摘要 / 输出 JSON / 调用了什么模型 / 耗时 / 成功标志。

查看方式：

  • API：GET /api/interpret/<id>/agent-trace
  • 可视化：浏览器打开 http://localhost:8080/telemetry.html?rid=6

为什么 trace 重要？没 trace 你只看到"AI 输出了一段话"，黑盒。有 trace 你能看到分类对没对、检索拉到哪些牌、生成多久、审查打几分。这是 Agent 工程跟普通 LLM 调用最大的差异之一。

  • 项目的 4 步管道里，哪一步在 stream 开始前跑？哪一步在 stream 结束后跑？为什么？
  • 如果嵌入模型挂了但本机 LLM 还活着，用户能看到解读吗？质量会差在哪？

05评测与可观测性

这一组词是 Agent 项目跟玩具项目最大的差距。

Golden Set（黄金集） golden set / eval set

手工准备的一批"标准考题"，每道题有期望答案。每次系统改动跑一遍这套题看分数变化。

项目里：evals/golden_set.json 30 道，5 个 topic 各 6 题： 
{"id": "career-01",
 "topic": "career",
 "question_zh": "我应该跳槽吗？",
 "question_en": "Should I change jobs?",
 "cards": [{"card_id": 9, "is_reversed": false}, ...]}

为什么不靠"我自己点几下感觉看看"？因为人测试不一致、不可重复、规模小。Golden set 是工业级模型开发的标准做法。

LM-as-judge（LM 当评委） LLM-as-judge

用一个（通常更强的）LLM 给被测 LLM 的输出打分。

类比：新人翻译的稿子让资深翻译审一遍。资深翻译不重新译，只评估。
实现：evals/judge.py 用 OpenRouter 上的 qwen-2.5-72b-instruct（72B 大模型）当评委，5 个维度各打 0-5 分：
  • relevance — 是否答了用户的问题
  • card_grounding — 是否真正用了抽到的牌
  • coherence — 是否自然散文（而非列表）
  • specificity — 是否具体而非空话
  • style_match — 是否符合所选风格

核心设计：评委用比生成器更强的模型 + 不同来源（云端 vs 本地），避免"自己改自己卷子"。

Rubric（评分表） rubric

事先定好的"打分维度 + 各维度怎么打分"的明文规则。让评测可复现。

例：项目的 rubric 在 evals/judge.py:RUBRIC_AXES。5 维 × 各 5 分 = 25 总分，标准化到 /10。
分类准确率 classification accuracy

分类器预测对的数量 / 总数量。

项目实测：27 / 30 = 90.0%。健康类 6 题对 4 题（66.7%）是最差的 — 心理咨询 / 焦虑被分到了 general。这是真实可改进的信号，写进了 ARCHITECTURE 的"已知缺口"。
可观测性 observability

系统出问题时，你能多快/多容易看清"内部发生了什么"。可观测性强 = 调试和监控容易。

项目里的可观测性栈：
  • agent_steps 表 — 每次推理 4 步全记下
  • telemetry.html — 用浏览器看任一 reading 的 trace 时间线
  • docs/evals/eval-*.md — 每次跑评测自动生成的报告

跟它对比的反例：黑盒 — 用户报告"AI 答非所问"，你只能干瞪眼。

Mock（模拟） mock

测试时把外部依赖替换成假的，让测试不需要真的网络/模型/数据库。

关键技巧：项目里 92 个 Python 测试，零个真的调 Ollama。所有 LLM 调用都被 unittest.mock.patch 替换： 
with mock.patch.object(interpret_agent, "call_ollama_json",
                       return_value={"topic": "career", ...}):
    step, result = interpret_agent.classify(...)
这样 CI 在无 GPU 的小机器上也能跑测试。

  • 为什么不能让被测的本地 7B 模型自己给自己打分？
  • "健康类准确率 66.7%" 这个数字是什么含义？怎么算出来的？
  • 如果你不写 mock，测试会出什么问题？

06工程概念（不是 AI 专属，但读项目必备）

幂等 idempotent

同一操作执行多次跟执行一次效果一样。

类比：电梯按钮 — 你按 10 下跟按 1 下结果一样（电梯只会来一次）。"删除文件 X"是幂等的；"账户余额减 100" 不是。
例：build_index() 是幂等的 — 跑 100 次和跑 1 次都是 156 条嵌入。第二次开始它直接短路返回，0 成本。
UTF-8 UTF-8

世界上最通用的字符编码。中文、英文、emoji 全部能正确表达。

项目踩过的坑（写在 CLAUDE.md）：
  1. Windows 上 Python 默认 HTTP body 可能丢中文 → 手动 json.dumps(..., ensure_ascii=False).encode("utf-8")
  2. python -m json.tool 在 Windows 控制台用 cp936 重解码 UTF-8 → 看起来乱码但数据本身没坏
本地优先 local-first

数据和计算优先在用户本机完成，云端只是补充。

体现：Ollama 跑在你本机，SQLite 也在本机，OpenRouter 只在 Ollama 挂了或显式选 backend 时才用。没账号没注册没上传。这也是为什么项目能"断网继续用"。
单元测试 / 集成测试 / E2E unit / integration / e2e test
层级测什么例子
Unit单个函数_cosine([1,0,0], [0,1,0]) == 0
Integration几个组件协作分类器→检索器→prompt builder，mock LLM
E2E跑完整真实路径启动服务器，浏览器自动点按钮，看输出
项目主要在 Unit + Integration 层（92 个 Python 测试 + 6 个 JS 测试），E2E 用手工 + Playwright（截图验证）。
回归测试 regression test

为已知 bug 写一个测试，防止它再回来。

实例：card_id 字段被漏的那次 bug 修复后，我加了 test_load_reading_for_interpret_preserves_card_id — 任何人未来再动那段 transform 都会让这个测试挂。
并发 / 锁 concurrency / lock

多个请求同时跑时怎么协调。锁 = "这把活儿一次只能一个人干"。

实例：同一个 reading 不允许两个解读同时跑（避免数据库错乱）。server.py:_INTERPRET_LOCKS 用 threading.Lock() 一把锁一个 reading_id，撞上返 HTTP 409。
优雅降级 vs 快速失败 graceful degradation vs fail-fast

用户路径上 → 优雅降级（部分功能可用胜过完全挂掉）。开发/启动阶段 → 快速失败（早暴露问题胜过隐藏）。

对比：
  • 解读流里嵌入器挂了 → 优雅降级到 canonical 检索（部分功能）
  • 启动时数据库连不上 → 快速失败，根本起不来（早暴露）
